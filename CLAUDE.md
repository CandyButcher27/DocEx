# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this project is

A document field-extraction pipeline: scanned/uploaded PDFs (or PNG/JPG, auto-converted) go through OCR, and an LLM reads the OCR output to pull out fields as `{field: value}` pairs. The **current main deliverable** is the *template-driven* extraction path (`/run_template` in `extract_ui.py`): rather than the user typing field names, the full field set is generated from a fixed schema (`field_spec.json`, built from the GSS schema Excel) and the pipeline fills it, decodes coded values, validates formats, flags low-confidence cells, and emits JSON in the exact nested shape of `template.json`. There are also two older workflows — a **template-authoring tool** (`template_tool.py`, draw field boxes on a clean docx→pdf) and the original **ad-hoc extraction** (`/run_llm`, user types field names → CSV). The authoring-tool yaml coordinates are still **not** consumed by the runtime path.

Everything else is grouped:

- **`tools/`** — standalone/experimental scripts, none imported by the runtime: `template_tool.py` (+`.html`), `overlay_boxes.py`, `paddle_page_ocr.py`, `crop_test.py`.
- **`tests/`** — CLI harnesses `test_run.py`, `test_anchor.py`, `test_page_by_page.py <pdf> <page_number>` (each has a `sys.path.insert` shim so `from ocr_engine import …` resolves the root modules when run as `python tests/test_run.py <pdf>`). `test_page_by_page.py` scopes the whole cascade (`reading_order`/anchor/OMR/classify) to one page's OCR entries by filtering `ocr_entries` before calling `extract()` — a dev/debug harness only, production stays whole-doc.
- **`scratch/`** — gitignored fixtures/caches (`*.ocrcache.json`, sample PDFs).

### Template-driven extraction — the pieces
- **`template.json`** — the master target shape: every field that can appear in any doc, nested by section (`loan_details`, `insured_details`, `nominee_details[]`, `address_details[]`, `medical_lifestyle_questions[]`, `declaration[]`, `mph_section`, …). Pipeline output must match this shape.
- **`GSS-SchemaSummary-V3(Mar-30) 2.xlsx`** — source schema. Sheet `Proposal Schema` = field label ↔ JSON path (`Field ID`) ↔ `Master` (Yes = coded/lookup field). `Proposal Mapping` adds data types + allowed-value enums. `Medical Questionnaire` / `Declarations` = question code → text.
- **`code_mapper.json`** — the "Group Asia" code dictionary (external; user-supplied, NOT in the Excel): maps human values → codes for coded fields (`Male`→`G001`, `Salaried/Professional`→`OC001`, `Spouse`→`R001`, address type, education, nationality, language, country code, relationship, plus `medicalQuestionOptions` and `declaration` code→text).
- **`build_field_spec.py`** → **`field_spec.json`** — flattens `Proposal Schema` into 106 field specs `{path, label, section, type, coded, repeat_group}`, attaching `options`/`allowed_values` from `code_mapper.json` to coded fields. System fields (uuids, timestamps, premium calcs, base64) are dropped. Re-run this if the Excel or mapper changes.
- **`field_extractor.py`** — the runtime engine (`extract(ocr_entries, pdf_path=..., threshold=0.95)`); see Architecture below.
- **`validators.py`** — format/business checks by field (PAN, IFSC, PIN, mobile, email, ABHA, date→`dd-mm-yyyy`, amount, digits, percentage). Pass → value normalized; **fail → field forced to `NOT_FOUND`** (shows as NO OUTPUT, reviewer fills).
- **`ocr_engine.py`** — shared PaddleOCR (single global engine, `cpu_threads=8`, `DPI=150`); `run_ocr_on_pdf`, `ocr_image`, `render_pages`. Both `extract_ui.py` and `anchor_fill.py` import from here.
- **`anchor_fill.py`** — second-pass recovery (see cascade below).
- **`tests/test_run.py <pdf>`** — CLI harness: OCR a scan → `extract()` → prints timing + found/low/anchor counts → writes `test_output.json`.

## Running things

No test suite, no build step, no lint config — this is a set of standalone Python scripts with local HTTP servers, run directly.

```powershell
# always run inside the venv
.venv\Scripts\python.exe <script>.py
```

- **Extraction UI** (main deliverable): `python extract_ui.py` → `http://localhost:8002`. Upload a PDF/PNG/JPG, hit Extract → OCR → LLM (template-driven, `/run_template`) → reviewer table (editable, yellow = low confidence / anchor-recovered, dashed = NO OUTPUT) + live JSON panel → Download JSON. (The old `/run_llm` add-your-own-fields + CSV flow still exists server-side.)
- **CLI test harness** (no browser): `.venv\Scripts\python.exe tests\test_run.py scanned_docs\<file>.pdf` — runs the full template pipeline on one scan, prints timing + found/low/anchor counts, writes `test_output.json`.
- **Template field-authoring tool**: `python tools\template_tool.py` → `http://localhost:8001`. Pick a template from `proper_docs/` (docx auto-converted to PDF via Word COM, cached in `proper_docs_pdf/`), draw a box per field, name it, set type (string/number/checkbox/date/alphanumeric) and required flag. Saves to `templates/<template_name>.yaml`.
- **Crop tool** (early prototype, scanned_docs only): `python crop_tool.py` → `http://localhost:8000`. Draws + saves single crops to `cropped_images/`.
- **Standalone OCR scripts** (engine comparison / one-off use, not wired into the UIs): `paddle_ocr.py`, `rapidocr_run.py`, `tesseract_run.py`, `run_trocr.py` — each reads a folder of cropped images (`test_crop/` or `cropped_images/`) and writes a JSON of `{text, avg_confidence, ...}` per file. `paddle_page_ocr.py` and `overlay_boxes.py` are page-level (not crop-level) equivalents: the former OCRs a whole rendered page image into a bbox-annotated JSON, the latter draws a template's stored yaml boxes onto a scanned page image so you can visually check alignment drift.

All three local servers use the same pattern: stdlib `http.server.BaseHTTPRequestHandler`, no framework (Flask/FastAPI are not installed — don't add them without asking). Each serves its own `.html` frontend at `/` and JSON/PNG over a handful of `GET`/`POST` routes. Multipart file uploads are hand-parsed (`parse_multipart` in `extract_ui.py`) rather than using `cgi` (deprecated) or a form library.

## Ingestion gate (`ingest_gate.py`)

Runs **before** extraction and **hard-rejects** a bad upload with a specific reason, so garbage never reaches the extractor. `check(pdf_path, ocr_entries=None)` runs the pre-extraction checks fail-fast (cheapest first) and returns `{ok, reason, detail, ocr}`; `check_mandatory(fields)` is a separate post-extraction check (needs the extractor's field states). Wired into `extract_ui.py` `/run_template`: gate before `extract`, mandatory after; on any failure the route returns `{"rejected": true, "reason": …}` and `extract_ui.html` shows a red reject banner instead of the reviewer table. The checks:

1. **Blur** (`check_blur`) — variance-of-Laplacian (`cv2.Laplacian(...).var()`) per rendered page, after downscaling the long side to `BLUR_MAX_SIDE=1500` so the metric is resolution-normalized. Worst page below `BLUR_THRESH=100` → reject "blurred". (Measured: real scans ~3000–6500; a `GaussianBlur(6)` copy ~2 — huge margin.) Runs before OCR (only needs the render).
2. **Template match** (`match_template`, TF-IDF cosine) — the accept-list is `proper_docs/*.docx`, indexed by `build_template_store.py` into `data/template_store.json` (hand-rolled TF-IDF: python-docx reads table-cell text → sublinear-TF × smoothed-IDF, L2-normalized per template; no sklearn). At ingest, each page's OCR text is vectorized in the store vocab and cosined against every template; doc-level score = max over pages. Below `MATCH_THRESH=0.25` → reject "unrecognized form". (Measured: real GCL scan 0.82 doc-level; lorem/bank-statement text 0.11.)
3. **Mandatory fields** (`check_mandatory`) — after extraction, `MANDATORY = [insured_details.first_name, insured_details.pan_number]` must each have field `state == "found"` (`no_output`/`blank`/absent → fail). PAN already routes through `validators` so an invalid PAN is `NOT_FOUND` → correctly triggers reject. Fail → reject "required field(s) missing: …". **DOB deferred**: insured date-of-birth is absent from the source Excel `Proposal Schema` (so `field_spec.json` has no insured DOB and the pipeline can't extract it), even though `template.json` includes `data.insured_details.date_of_birth`. To make DOB mandatory, first add `insured_details.date_of_birth` to the spec.

**Multi-document detection — evaluated and dropped.** A per-page "one kind per PDF" check (reject if any page fails to match a template) was prototyped but removed: a real GCL submission contains a number-heavy **premium/benefit-illustration page** whose cosine (0.13 on the HDF scan) is indistinguishable from a genuinely foreign page (lorem/bank-statement text 0.11), and the 4 templates are near-duplicates anyway (2 doc-types — DOGH declaration + LFQ questionnaire — × 2 products; LFQ pair cosine 0.996, DOGH pair 0.943) so a single packet legitimately spans multiple template kinds (BPR pages argmax to Premier_LFQ / Secure_LFQ / Premier_DOGH). No page-level score floor separated real-but-sparse pages from foreign pages without false-rejecting real docs, so multi-doc PDFs are left to the human reviewer.

Rebuild the template store (`python build_template_store.py`) whenever `proper_docs/` changes. Thresholds are module constants at the top of `ingest_gate.py`; `python ingest_gate.py --calibrate "<glob>"` prints per-file sharpness + template cosines (and the template×template matrix) for retuning.

## Architecture

**`extract_ui.py` / `extract_ui.html`** — the runtime pipeline:
1. `/upload` — accepts PDF or image (PNG/JPG auto-converted to a single-page PDF via Pillow, `image_bytes_to_pdf_bytes`). Stores per-doc state in the in-memory `DOCS` dict keyed by `doc_id` (not persisted — restarting the server loses all uploaded docs).
2. `/run_ocr` — renders every page via `pdf2image.convert_from_path` at `DPI = 150`, runs `PaddleOCR` (`use_doc_orientation_classify/unwarping/textline_orientation` all disabled — the OCR is not correcting skew/rotation, see note below) on each page, returns line count. OCR entries (`text`, `confidence`, `bbox`, `page`) are cached on the doc, not returned to the client.
3. `/run_llm` — (legacy ad-hoc path) sends the full OCR entry list plus the user's field-name list to `llm_client.run_extraction`, using `EXTRACTION_PROMPT` (asks for a plain `{field: value}` JSON, `"NOT_FOUND"` if absent). Response is regex-extracted (`\{.*\}`) and JSON-parsed defensively.
4. `/run_template` — (current main path) calls `field_extractor.extract(doc["ocr"], pdf_path=doc["pdf_path"])`. Returns `{threshold, flat, template, fields[]}` where `template` is the nested `template.json`-shaped output and `fields[]` carries per-field review metadata. `extract_ui.html` is now a **reviewer UI** for this: editable table grouped by section, coded fields as dropdowns (human text stored as code), **yellow rows when confidence < 95%** or anchor-recovered (verify), NO-OUTPUT rows dashed, a **live JSON panel** that rebuilds on every edit (JS `assemble` mirrors the Python one, incl. `isAnswer` derivation for medical/declaration), and Download JSON.

**`field_extractor.py` — the extraction cascade** (`extract()`):
1. **Pass 1 — OCR reading-order + batched LLM.** `reading_order()` clusters OCR tokens into visual rows (sort by y then x) so a printed label and its value sit on one line (a single 106-field prompt made the model silently drop most fields; reading order lets it associate label→value). `_run_batches()` then makes **several small LLM calls** (~15 fields each; repeat groups and fixed groups as their own calls) because the model under-returns on large asks — batching lifted doc2-page recall 26→~40. `llm_client` uses `temperature=0`. `_BATCH_HEADER` tells the model printed labels differ from field names, to return NOT_FOUND for blank fields, and never to copy a value across sections. Results merge into a flat `{path: human_value}`. **Precision guards** run after all recovery: (A) drop a value in a "suspect" optional section (`proposer_details`, `disability_declarant`, `vernacular_declarant`, `mph_section`) whose normalized value is a substring-match of a value in a real section (echo of the insured); (B) null a person-section that has no `first_name`. Batching raises recall but the model hallucinates insured data into blank optional sections — these deterministic guards remove that.
2. **Pass 2 — anchor recovery** (`anchor_fill.anchor_fill`, only if `pdf_path` given). For each still-`NOT_FOUND` singleton text field (suspect sections excluded): match its printed label — using `ALIASES` (e.g. `loan_account_number` → "Loan A/c No") since form wording differs from schema — then **take detected OCR tokens to the right of the label directly** (stopping at the next label), only re-OCRing a crop when that region is empty (true handwriting miss). Recoveries capped at `MAX_VALUE_LEN`/`MAX_VALUE_TOKENS` (reject paragraphs), flagged `low` + note "recovered via anchor — verify".
2b. **Classification — BLANK vs NO_OUTPUT** (`anchor_fill.classify_missing`). Each still-missing singleton text field: if its label isn't found on the form → **`blank`** (form left it empty / not on this page — VLM skips); if the label is found but the value region has ink (`_ink_ratio` > `BLANK_INK_THRESH`) → **`no_output`** (content present but unread — VLM target). Three field states now flow to the UI: `found` (yellow if `low`), `blank` (neutral grey), `no_output` (dashed — needs attention). Blanks are omitted from the JSON like any non-value.
3. **Pass 2.5 — checkbox OMR** (`checkbox_omr.detect`, coded singleton fields still NO OUTPUT). For each coded field, find its option labels (from `code_mapper`, printed text → reliable OCR) in the pass-1 lines, measure ink in the box region left/right of each option label, pick the marked one → map label→code. Guards: a field is only treated as a checkbox group if ≥`MIN_GROUP_FRAC` (0.4) and ≥2 of its options appear as printed labels (rejects stray/handwritten matches like a nominee "Father"); symbol-bearing options (`>=50%`/`<50%`) match symbols exactly (the tokenizer alone collided them); cells claimed by >1 option are dropped unless the collision is 2-3 options sharing one OCR-merged bbox (e.g. "Graduate & Postgraduate" printed as one line) — those get proportionally split by character offset (`_split_merged_options`) so both still compete on ink instead of being auto-dropped; and option labels are spatially clustered so a cross-region match (e.g. "Agriculture Loan" in the loan-type field matching the occupation option) is discarded. Ambiguous (no box beats runner-up by `MARGIN`) → left NO OUTPUT. Recovered fields flagged `low` + note "checkbox detected — verify". `checkbox_omr.detect_ticks` additionally OMRs Yes/No tick-matrix answers (`medical_lifestyle_questions[i].answer`) by finding the section's single "Yes  No" column header once, then measuring ink at each question's own row under those two x-columns. **Not extended to `declaration[]`** — that section doesn't show the same standalone column-header signal in the docs studied, so a naive copy of the medical logic would risk guessing a column pairing that isn't really there; `declaration[*].answer` stays NOT_FOUND until a real header signal is confirmed. Known tuning gaps: symbol-only option labels (`>=50%`) fail the tokenizer; medical tick-OMR recovers only a small fraction of questions per doc (header-row text matching is narrow — may need a looser header-phrase match).
**VLM bbox-locator — evaluated and dropped.** A VLM-locator pass (VLM returns value bounding boxes only, Paddle OCR reads the crop — never VLM extraction) was prototyped but removed: no box-grounding-capable VLM is available on the current stack. Ollama's vision models (`gemma3:*`, `gemma4:31b`) return plausible-but-spatially-wrong boxes (tested: a PAN box landed on the gender row); the one grounding-capable Ollama model (`gemini-3-flash-preview`) needs a paid subscription (403); direct Gemini is 429 rate-limited and excluded by preference. anchor + OMR + batched pass-1 already recover on-page readable fields, and a human reviews every field, so the marginal value didn't justify the access cost. If a grounding model (Qwen2.5-VL, Gemini-class) becomes available, re-add a bbox→crop→Paddle-OCR pass targeting only `no_output` fields.
Then: `validators.validate` on found non-coded fields (fail→`NOT_FOUND`), `_decode` (human→code, index-agnostic so it works for any repeat index), per-field `confidence` (max conf of OCR lines containing the value), and `assemble` → nested `template.json` shape. `_finalize_fixed` sets `answer`/`isAnswer`/`description` on medical & declaration entries.

**Design rule (hard):** the **VLM must never read/extract a field value** — it may only *locate* (return coordinates for cropping). PaddleOCR always does the actual reading. This is a fixed product constraint from the user's manager.

**`llm_client.py`** — thin wrapper around Ollama Cloud's OpenAI-compatible endpoint (`OLLAMA_BASE_URL=https://ollama.com/v1`, no `openai` SDK dependency, just `requests`). Config comes from `.env` (`OLLAMA_API_KEY`, `OLLAMA_BASE_URL`, `OLLAMA_MODEL` — currently `gpt-oss:120b`, chosen for reliable structured-JSON output over the previous `gemma4:31b`). `run_extraction(ocr_json, prompt, model=...)` is the one entry point other scripts call.

**`template_tool.py` / `template_tool.html`** — authoring tool for per-template field definitions. Converts `proper_docs/*.docx` to PDF via `docx2pdf` (needs MS Word installed — Windows COM automation, not portable). Saves field boxes as fractional (0–1) `{x, y, w, h}` coordinates plus `name`/`type`/`required`/`page` to `templates/<name>.yaml`. These yaml files are the intended source of truth for "where is field X on this document" but **are not currently consumed by `extract_ui.py`** — the runtime path re-discovers fields by name via the LLM reading raw OCR text, not by looking up template coordinates.

**Known gap discovered via `overlay_boxes.py`**: template yaml coordinates are fractional/percentage-based and only line up correctly with a scan if the scan has the same crop/aspect/rotation as the clean template. Real scans have skew and scan-bed margins that clean docx renders don't, so directly reusing template boxes on a scan requires either deskew/registration or anchor-relative extraction (locate boxes via OCR'd label text + stored offset) — neither is implemented yet.

## Known constraints / things not to "fix" without asking

- **`enable_mkldnn=True` crashes** on this machine's PaddlePaddle build (`NotImplementedError: ConvertPirAttribute2RuntimeAttribute ... onednn_instruction.cc`). Keep it `False` in every `PaddleOCR(...)` call. This was tested and reverted — don't re-enable it as a "speed fix" without expecting the same crash.
- **PaddleOCR is CPU-only, single global engine instance** — now lives in `ocr_engine.py` (`get_ocr`, `_engine` module global, `cpu_threads=8`), imported by both `extract_ui.py` and `anchor_fill.py`. Cold start ~15–30s per process; OCR is the dominant cost, ~333s for a dense 3-page form on this 8-core CPU (no GPU present).
- **OCR speed — measured findings (don't re-litigate):**
  - **Parallel pages via Python threads DEADLOCKS** (ThreadPoolExecutor + per-thread engine hung with ~0% CPU). PaddleOCR CPU inference already saturates all 8 cores per image, so page-level parallelism gives ~nothing anyway. Do not reintroduce threaded page OCR.
  - **Model choice** (measured on `BPR000513405100.pdf`, 3 pages): default `PP-OCRv6_medium` det+rec = 333s, most accurate (0 validation fails). `PP-OCRv5_mobile` det+rec = 175s but loses dense numerics (PIN/account/DOB → validation fail). `mobile det + v6 rec` = 221s, still 1–2 numeric fails (mobile detection draws worse boxes). Current default is reverted to accurate v6 (no model-name overrides). mkldnn still crashes; no clean CPU speedup exists — GPU is the only large lever and there's no NVIDIA GPU.
- **Handwriting is a localization problem, not a recognition one.** The real scans are hand-filled. PaddleOCR's recognizer reads handwriting **very well on a tight crop** (0.94–0.999 conf on cropped name/PAN/loan-no), but full-page **detection** misses/merges dense handwritten value regions, so those fields come back NO OUTPUT. This is why the anchor pass (crop the value region beside its label, re-OCR) recovers them — see the `field_extractor` cascade. Checkbox/tick fields (gender, occupation, nationality, education, …) are a **separate** problem — not text at all; no OCR reads a tick. Handled by `checkbox_omr.py` (OMR: locate printed option labels via OCR, measure ink in the box beside each, winner→code). Verified: gender/occupation/nationality recovered correctly on `BPR000513405100.pdf`. Medical Yes/No ticks partially OMR'd (`detect_ticks`); declaration ticks not yet (see cascade note above).

### No-output diagnostic breakdown (measured across 4 cached scans, this session)

Running `scratch/diagnose_no_output.py` against `data/field_spec.json` metadata (coded vs plain-text vs repeat-group) showed the `no_output` bucket (fields with printed ink present but never recovered) splits into exactly two causes — no third category once repeat-group path lookups are normalized (strip `[i]` before matching `field_spec` keys, which only store index `[0]`):
- **~76% plain-text fields where anchor was attempted and failed.**
- **~24% coded checkbox fields where OMR was attempted and the ink was ambiguous/no match.**

Within the plain-text bucket, one pattern dominated: **`nominee_details[i].*` fails on nearly every field, every doc.** Root cause: `nominee_details` is printed as a **table** (one header row concatenating all column labels, then one x-aligned data row per nominee below it — not a printed "Label: value" line), which `anchor_fill.py`'s row-based heuristic (`_find_anchor`/`_same_row`, value-right-of-label-on-same-line) structurally cannot match; `field_extractor.py` also excludes all `repeat_group` fields from the anchor pass entirely today. `nominee_table.py` adds a table-column recovery pass scoped to `nominee_details` only — locates the header row, derives each column's x-band, locates each nominee's own data row, and pulls the token(s) inside each column's band. `address_details` (the other repeat_group) is a plain label:value layout, not a table, and was deliberately NOT swept into this — don't assume the same table logic applies there without separately verifying its printed layout first. `address_recovery.py` handles `address_details`' own gap separately: that section prints as one composite "Communication/Permanent Address" label + Landmark/State/PIN row, not literal "Address Line 1/2/3" labels, so it needs its own line-splitting recovery (`extract_address_lines`) rather than the row-based anchor heuristic.

**`nominee_details` blank-vs-no_output classification — fixed for the non-coded leaves (verified on `BPR000513405100.pdf`).** `field_extractor.py`'s blank-vs-no_output classification (`anchor_fill.classify_missing`) explicitly excludes every `repeat_group` field, so any `nominee_details[*]` leaf still `NOT_FOUND` after `extract_nominee_table` used to default straight to `no_output` — even when genuinely blank (no printed column at all, e.g. `bank_branch`/`city`/`state`/`pin_code`/`address_line_2`/`address_line_3`/`mobile_country_code`/`other_relation`/`account_holder_name`; a printed column with an empty cell, e.g. `account_number`/`ifsc_code`; the unfilled appointee block above the table; or the never-printed system field `id`). `nominee_table.classify_nominee_missing` (+ `_classify_appointee` helper) now covers this: no column band for a leaf → `blank`; column band present but ink-check empty → `blank`; appointee label:value block ink-checked within a y-window scoped to *that table's* header (avoids colliding with the unrelated "Date of Birth:" labels for insured/proposer elsewhere on the page); `id` is always `blank` (never a printed field, same category as the uuid/timestamp fields `build_field_spec.py` already drops). Wired into `field_extractor.py` right after the `nominee_missing`/`extract_nominee_table` call, merged into `state_override` (only when the field is still `NOT_FOUND`, so it can never override an actually-recovered value). On `BPR000513405100.pdf` this dropped nominee `no_output` 19→8. **Residual gap, not fixed by this pass**: `nominee_details[*].state`, `.appointee_gender`, `.appointee_relationship_with_nominee`, `.mobile_country_code` are `coded` (Enum) fields, which never reach `nominee_missing` (that list explicitly filters `not f["coded"]`) — coded fields route to `checkbox_omr.detect` instead, which *also* excludes `repeat_group` fields. So coded nominee columns are unreached by either pipeline. `address_details`' repeat_group exclusion from `classify_missing` is the same underlying pattern and is also still unfixed — out of scope of the nominee-specific pass, don't assume it's covered.

**Ollama Cloud non-determinism affects more than field values** — rerunning the identical cached-OCR + code produced a *different number of `nominee_details[]` entries* across two runs (1 nominee detected vs 2). This means overall match-rate / no_output counts will wobble slightly run-to-run even with nothing changed; don't over-read small deltas between two runs as a regression or improvement without checking the actual field-level diff.

### Doc-type registry — config-driven specialization (thin wrapper today)

`doc_type_registry.py` + `data/doc_type_registry.json` add one lookup point, keyed by the exact `doc_kind` string `ingest_gate.match_template` returns (e.g. `"GCL Secure_LFQ"`), resolving to `{field_spec_path, code_mapper_path, include_medical}`. `extract_ui.py`'s `/run_template` resolves `doc_kind` through the registry and passes the resolved spec into `field_extractor.extract(spec=..., doc_type=doc_kind)`; unregistered/unknown `doc_kind` falls back to the universal `field_spec.json` (no new rejections). Today this is a no-op for the one registered entry (same spec/mapper file as the default) — the payoff is only realized once a genuinely different lender template (axis bank, toyota, ujjivan, … seen in `New forms/`) gets its own registry entry with its own spec/mapper, without touching the GCL path. Not yet exercised against a second template — that's the next thing to validate.

### Doc-type-aware extraction — implemented (medical-section gating only)

`ingest_gate.match_template` classifies every upload against the 4 known templates (2 doc types × 2 products, `data/template_store.json`). `extract_ui.py`'s `/run_template` route now threads `gate["detail"]["match"]["doc_kind"]` into `field_extractor.extract(..., doc_type=doc_kind)`. Bias, not gate: the full `field_spec.json` master schema is still always run for every non-medical section regardless of doc_type — the **only** thing doc_type controls is `include_medical_for(doc_type)` (`field_extractor.py`), which skips the `medical_lifestyle_questions` LLM batch (and therefore its metas/tick-OMR pass) when `doc_type` contains `"DOGH"`.

This is deliberately narrow, not the general "reorder every batch / route every recovery pass by type" idea floated earlier. Reasons it's safe where that broader idea wasn't:
- **Verified as a real content difference, not an inferred one**: grepped all 4 `proper_docs/*.docx` against `code_mapper.json`'s 9 medical-question texts — every DOGH template matched 0/9, every LFQ template matched 7/9. DOGH forms genuinely carry no medical section; asking the LLM for it just wastes a batch call and risks hallucination into a section that isn't printed.
- **Classification confidence checked before trusting it**: template×template cosine shows DOGH↔LFQ cross-similarity ~0.87–0.89, clearly separated from same-type product-pair near-duplicates (Premier/Secure DOGH 0.943, Premier/Secure LFQ 0.996). So an explicit `"DOGH"` substring match in `doc_kind` is trustworthy; the earlier-flagged 0.996 near-duplicate risk is specifically the Premier-vs-Secure axis, which never mattered here since both products within a doc type share the identical field set (confirmed no other field differs between Premier/Secure of the same type).
- **Safe-default direction**: `include_medical_for(doc_type)` returns `True` (include medical, i.e. today's original always-run behavior) for `None`, unmatched/unknown `doc_kind`, or an `LFQ` match — only an explicit `"DOGH"` match skips it. Getting the classification wrong in the DOGH direction on an actual LFQ doc would just mean a batch never asked (a miss caught by a human reviewer since the field stays absent/blank); it can't produce a wrong answer.
- Untouched: `nominee_table.py` (table-column recovery, general — not gated by doc_type, applies whenever `nominee_details` prints as a table), `checkbox_omr.detect` (general-purpose OMR), `checkbox_omr.detect_ticks` (medical Yes/No tick-OMR, still weak ~19% recall — see below, unrelated to this gating), declaration tick-OMR (still not attempted, no signal exists per below).

**Declaration Yes/No tick-OMR — investigated, not extended.** Checked real OCR layout across all 4 cached docs for the true `declaration[]` paragraphs (the 6 long statements in `code_mapper.json`'s `declaration` list, e.g. code `20003`/`20004`/`20005`): they show **one shared "[Please tick applicable box]" phrase covering multiple statements together**, no standalone Yes/No pair and no per-statement tickbox — there's no 1:1 signal to OMR per declaration field without guessing a pairing that doesn't exist. (One doc's `no_output` list showed what looked like a declaration-section Yes/No matrix — that was actually `medical_lifestyle_questions` mislabeled by a loose "declaration" keyword search catching that doc's combined page title "...Questionnaire Cum Declaration Form", not real declaration content.) Confirms the existing note above — leave `declaration[*].answer` as-is.

**Medical tick-OMR recall is weak (~19%, 6/32 across the 4 docs) — root cause found, a fix attempted and reverted as unsafe.** `checkbox_omr._find_question_row` matches a question's first 12 tokens against a **single OCR entry**; medical questions are 60-100+ word paragraphs that wrap across many short OCR lines, so no single line ever carries enough of the question's tokens to clear the 0.5 match threshold — only short one-line questions (10002, 10006, 10008) recover reliably. Tried fixing via each question's printed row-number marker (`"1)"`, `"2)"`, ...) instead of content-matching: recall improved on some docs but a real doc (`924030061722211`) shows the marker sequence **doesn't align 1:1 with schema index** — physical height/weight fields consume marker `"1)"`, shifting the real Yes/No question list to start at `"2)"`. A position-based index→marker mapping there would silently produce a **wrong answer** (not just a miss) — worse than leaving it `no_output` for review. Reverted; `checkbox_omr.py` is back to the original content-matching version. A safe fix would need each candidate marker's nearby text separately verified against the expected question (position as a *candidate generator*, content-match as the *acceptance gate*) before trusting it — not yet implemented.
