# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this project is

A document field-extraction pipeline: scanned/uploaded PDFs (or PNG/JPG, auto-converted) go through OCR, and an LLM reads the OCR output to pull out fields as `{field: value}` pairs. The **current main deliverable** is the *template-driven* extraction path (`/run_template` in `extract_ui.py`): rather than the user typing field names, the full field set is generated from a fixed schema (`field_spec.json`, built from the GSS schema Excel) and the pipeline fills it, decodes coded values, validates formats, flags low-confidence cells, and emits JSON in the exact nested shape of `template.json`. There are also two older workflows — a **template-authoring tool** (`template_tool.py`, draw field boxes on a clean docx→pdf) and the original **ad-hoc extraction** (`/run_llm`, user types field names → CSV). The authoring-tool yaml coordinates are still **not** consumed by the runtime path.

### Template-driven extraction — the pieces
- **`template.json`** — the master target shape: every field that can appear in any doc, nested by section (`loan_details`, `insured_details`, `nominee_details[]`, `address_details[]`, `medical_lifestyle_questions[]`, `declaration[]`, `mph_section`, …). Pipeline output must match this shape.
- **`GSS-SchemaSummary-V3(Mar-30) 2.xlsx`** — source schema. Sheet `Proposal Schema` = field label ↔ JSON path (`Field ID`) ↔ `Master` (Yes = coded/lookup field). `Proposal Mapping` adds data types + allowed-value enums. `Medical Questionnaire` / `Declarations` = question code → text.
- **`code_mapper.json`** — the "Group Asia" code dictionary (external; user-supplied, NOT in the Excel): maps human values → codes for coded fields (`Male`→`G001`, `Salaried/Professional`→`OC001`, `Spouse`→`R001`, address type, education, nationality, language, country code, relationship, plus `medicalQuestionOptions` and `declaration` code→text). `template_another.json` is a duplicate copy of this mapper.
- **`build_field_spec.py`** → **`field_spec.json`** — flattens `Proposal Schema` into 106 field specs `{path, label, section, type, coded, repeat_group}`, attaching `options`/`allowed_values` from `code_mapper.json` to coded fields. System fields (uuids, timestamps, premium calcs, base64) are dropped. Re-run this if the Excel or mapper changes.
- **`field_extractor.py`** — the runtime engine (`extract(ocr_entries, pdf_path=..., threshold=0.95)`); see Architecture below.
- **`validators.py`** — format/business checks by field (PAN, IFSC, PIN, mobile, email, ABHA, date→`dd-mm-yyyy`, amount, digits, percentage). Pass → value normalized; **fail → field forced to `NOT_FOUND`** (shows as NO OUTPUT, reviewer fills).
- **`ocr_engine.py`** — shared PaddleOCR (single global engine, `cpu_threads=8`, `DPI=150`); `run_ocr_on_pdf`, `ocr_image`, `render_pages`. Both `extract_ui.py` and `anchor_fill.py` import from here.
- **`anchor_fill.py`** — second-pass recovery (see cascade below).
- **`test_run.py <pdf>`** — CLI harness: OCR a scan → `extract()` → prints timing + found/low/anchor counts → writes `test_output.json`.

## Running things

No test suite, no build step, no lint config — this is a set of standalone Python scripts with local HTTP servers, run directly.

```powershell
# always run inside the venv
.venv\Scripts\python.exe <script>.py
```

- **Extraction UI** (main deliverable): `python extract_ui.py` → `http://localhost:8002`. Upload a PDF/PNG/JPG, hit Extract → OCR → LLM (template-driven, `/run_template`) → reviewer table (editable, yellow = low confidence / anchor-recovered, dashed = NO OUTPUT) + live JSON panel → Download JSON. (The old `/run_llm` add-your-own-fields + CSV flow still exists server-side.)
- **CLI test harness** (no browser): `.venv\Scripts\python.exe test_run.py scanned_docs\<file>.pdf` — runs the full template pipeline on one scan, prints timing + found/low/anchor counts, writes `test_output.json`.
- **Template field-authoring tool**: `python template_tool.py` → `http://localhost:8001`. Pick a template from `proper_docs/` (docx auto-converted to PDF via Word COM, cached in `proper_docs_pdf/`), draw a box per field, name it, set type (string/number/checkbox/date/alphanumeric) and required flag. Saves to `templates/<template_name>.yaml`.
- **Crop tool** (early prototype, scanned_docs only): `python crop_tool.py` → `http://localhost:8000`. Draws + saves single crops to `cropped_images/`.
- **Standalone OCR scripts** (engine comparison / one-off use, not wired into the UIs): `paddle_ocr.py`, `rapidocr_run.py`, `tesseract_run.py`, `run_trocr.py` — each reads a folder of cropped images (`test_crop/` or `cropped_images/`) and writes a JSON of `{text, avg_confidence, ...}` per file. `paddle_page_ocr.py` and `overlay_boxes.py` are page-level (not crop-level) equivalents: the former OCRs a whole rendered page image into a bbox-annotated JSON, the latter draws a template's stored yaml boxes onto a scanned page image so you can visually check alignment drift.

All three local servers use the same pattern: stdlib `http.server.BaseHTTPRequestHandler`, no framework (Flask/FastAPI are not installed — don't add them without asking). Each serves its own `.html` frontend at `/` and JSON/PNG over a handful of `GET`/`POST` routes. Multipart file uploads are hand-parsed (`parse_multipart` in `extract_ui.py`) rather than using `cgi` (deprecated) or a form library.

## Architecture

**`extract_ui.py` / `extract_ui.html`** — the runtime pipeline:
1. `/upload` — accepts PDF or image (PNG/JPG auto-converted to a single-page PDF via Pillow, `image_bytes_to_pdf_bytes`). Stores per-doc state in the in-memory `DOCS` dict keyed by `doc_id` (not persisted — restarting the server loses all uploaded docs).
2. `/run_ocr` — renders every page via `pdf2image.convert_from_path` at `DPI = 150`, runs `PaddleOCR` (`use_doc_orientation_classify/unwarping/textline_orientation` all disabled — the OCR is not correcting skew/rotation, see note below) on each page, returns line count. OCR entries (`text`, `confidence`, `bbox`, `page`) are cached on the doc, not returned to the client.
3. `/run_llm` — (legacy ad-hoc path) sends the full OCR entry list plus the user's field-name list to `llm_client.run_extraction`, using `EXTRACTION_PROMPT` (asks for a plain `{field: value}` JSON, `"NOT_FOUND"` if absent). Response is regex-extracted (`\{.*\}`) and JSON-parsed defensively.
4. `/run_template` — (current main path) calls `field_extractor.extract(doc["ocr"], pdf_path=doc["pdf_path"])`. Returns `{threshold, flat, template, fields[]}` where `template` is the nested `template.json`-shaped output and `fields[]` carries per-field review metadata. `extract_ui.html` is now a **reviewer UI** for this: editable table grouped by section, coded fields as dropdowns (human text stored as code), **yellow rows when confidence < 95%** or anchor-recovered (verify), NO-OUTPUT rows dashed, a **live JSON panel** that rebuilds on every edit (JS `assemble` mirrors the Python one, incl. `isAnswer` derivation for medical/declaration), and Download JSON.

**`field_extractor.py` — the extraction cascade** (`extract()`):
1. **Pass 1 — full-page OCR + LLM.** `build_prompt(spec)` lists non-repeating fields by path, requests variable repeat groups (`nominee_details`, `address_details`) as JSON arrays, and requests fixed groups (`medical_lifestyle_questions` 10001–10008, `declaration` 20001–20006) as `{code: Yes|No|NOT_FOUND}` answer maps. LLM returns one JSON object → parsed into a flat `{path: human_value}`.
2. **Pass 2 — anchor recovery** (`anchor_fill.anchor_fill`, only if `pdf_path` given). For each still-`NOT_FOUND` **singleton text** field: fuzzy-match its printed label in the pass-1 OCR lines → crop the region to the right of that label → **re-OCR the crop** with the same PaddleOCR → merged as the value. Recovered fields are flagged `low=True` + note "recovered via anchor — verify". (Coded/checkbox fields and repeat-group instances are skipped in v1.)
3. **Pass 2.5 — checkbox OMR** (`checkbox_omr.detect`, coded singleton fields still NO OUTPUT). For each coded field, find its option labels (from `code_mapper`, printed text → reliable OCR) in the pass-1 lines, measure ink in the box region left/right of each option label, pick the marked one → map label→code. Guard: a field is only treated as a checkbox group if ≥`MIN_GROUP_FRAC` (0.4) and ≥2 of its options appear as printed labels — this rejects stray/handwritten word matches (e.g. a handwritten "Father" in a nominee cell was being mistaken for the relationship option). Ambiguous (no box beats runner-up by `MARGIN`) → left NO OUTPUT. Recovered fields flagged `low` + note "checkbox detected — verify". Known tuning gaps: symbol-only option labels (`>=50%`) fail the tokenizer; medical/declaration Yes/No ticks (answer_field) not yet OMR'd.
4. **Pass 3 — VLM locator fallback** — *planned, not built.* For fields still NO OUTPUT, a VLM would return a **bounding box only** (never the value) → crop → re-OCR with Paddle.
Then: `validators.validate` on found non-coded fields (fail→`NOT_FOUND`), `_decode` (human→code, index-agnostic so it works for any repeat index), per-field `confidence` (max conf of OCR lines containing the value), and `assemble` → nested `template.json` shape. `_finalize_fixed` sets `answer`/`isAnswer`/`description` on medical & declaration entries.

**Design rule (hard):** the **VLM must never read/extract a field value** — it may only *locate* (return coordinates for cropping). PaddleOCR always does the actual reading. This is a fixed product constraint from the user's manager.

**`llm_client.py`** — thin wrapper around Ollama Cloud's OpenAI-compatible endpoint (`OLLAMA_BASE_URL=https://ollama.com/v1`, no `openai` SDK dependency, just `requests`). Config comes from `.env` (`OLLAMA_API_KEY`, `OLLAMA_BASE_URL`, `OLLAMA_MODEL` — currently `gpt-oss:120b`, chosen for reliable structured-JSON output over the previous `gemma4:31b`). `run_extraction(ocr_json, prompt, model=...)` is the one entry point other scripts call.

**`template_tool.py` / `template_tool.html`** — authoring tool for per-template field definitions. Converts `proper_docs/*.docx` to PDF via `docx2pdf` (needs MS Word installed — Windows COM automation, not portable). Saves field boxes as fractional (0–1) `{x, y, w, h}` coordinates plus `name`/`type`/`required`/`page` to `templates/<name>.yaml`. These yaml files are the intended source of truth for "where is field X on this document" but **are not currently consumed by `extract_ui.py`** — the runtime path re-discovers fields by name via the LLM reading raw OCR text, not by looking up template coordinates.

**Known gap discovered via `overlay_boxes.py`**: template yaml coordinates are fractional/percentage-based and only line up correctly with a scan if the scan has the same crop/aspect/rotation as the clean template. Real scans have skew and scan-bed margins that clean docx renders don't, so directly reusing template boxes on a scan requires either deskew/registration or anchor-relative extraction (locate boxes via OCR'd label text + stored offset) — neither is implemented yet.

## Known constraints / things not to "fix" without asking

- **`enable_mkldnn=True` crashes** on this machine's PaddlePaddle build (`NotImplementedError: ConvertPirAttribute2RuntimeAttribute ... onednn_instruction.cc`). Keep it `False` in every `PaddleOCR(...)` call. This was tested and reverted — don't re-enable it as a "speed fix" without expecting the same crash.
- **PaddleOCR is CPU-only, single global engine instance** — now lives in `ocr_engine.py` (`get_ocr`, `_engine` module global, `cpu_threads=8`), imported by both `extract_ui.py` and `anchor_fill.py`. Cold start ~15–30s per process; OCR is the dominant cost, ~333s for a dense 3-page form on this 8-core CPU (no GPU present).
- **OCR speed — measured findings (don't re-litigate):**
  - **Parallel pages via Python threads DEADLOCKS** (ThreadPoolExecutor + per-thread engine hung with ~0% CPU). PaddleOCR CPU inference already saturates all 8 cores per image, so page-level parallelism gives ~nothing anyway. Do not reintroduce threaded page OCR.
  - **Model choice** (measured on `BPR000513405100.pdf`, 3 pages): default `PP-OCRv6_medium` det+rec = 333s, most accurate (0 validation fails). `PP-OCRv5_mobile` det+rec = 175s but loses dense numerics (PIN/account/DOB → validation fail). `mobile det + v6 rec` = 221s, still 1–2 numeric fails (mobile detection draws worse boxes). Current default is reverted to accurate v6 (no model-name overrides). mkldnn still crashes; no clean CPU speedup exists — GPU is the only large lever and there's no NVIDIA GPU.
- **Handwriting is a localization problem, not a recognition one.** The real scans are hand-filled. PaddleOCR's recognizer reads handwriting **very well on a tight crop** (0.94–0.999 conf on cropped name/PAN/loan-no), but full-page **detection** misses/merges dense handwritten value regions, so those fields come back NO OUTPUT. This is why the anchor pass (crop the value region beside its label, re-OCR) recovers them — see the `field_extractor` cascade. Checkbox/tick fields (gender, occupation, nationality, education, …) are a **separate** problem — not text at all; no OCR reads a tick. Handled by `checkbox_omr.py` (OMR: locate printed option labels via OCR, measure ink in the box beside each, winner→code). Verified: gender/occupation/nationality recovered correctly on `BPR000513405100.pdf`. Medical/declaration Yes/No ticks not yet OMR'd.
- **`.env` holds real API keys** (`OLLAMA_API_KEY`, `GEMINI_API_KEY`) — already gitignored, never print full values, never commit.
- `proper_docs/` (real customer forms) and `templates/**/reference/` are gitignored — confidential source documents, don't try to commit or publish them.
- `scanned_docs/` is also gitignored (test scans) — safe to use locally for testing but don't assume it's tracked in git.
